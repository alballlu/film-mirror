# FilmMirror 面试复盘、冷启动与数据闭环方案

更新日期：2026-08-01

## 一、结论

FilmMirror 已具备“从 0 到 1 做出并上线 MVP”的证明力，但尚未形成“发现真实问题—定义指标—采集数据—验证方案—迭代复盘”的证据闭环。现阶段不应优先增加大量新功能，也不建议立刻分散精力做无关小程序；应先完成一轮真实用户验证和可复现的数据分析。

## 二、面试中已经能证明什么

1. 将“电影偏好”拆解为标签、六维画像和可解释推荐规则。
2. 设计深度画像与“今天看什么”两条使用路径，覆盖自我探索和即时决策场景。
3. 完成 TMDB、Cloudflare Pages Functions、缓存和本地降级等上线能力。
4. 根据输入与结果断裂、加载慢、按钮无反馈等问题完成多轮迭代。
5. 已有分享、换一批、想看、看过、不想看及原因反馈等闭环入口。

## 三、当前最缺的面试证据

### P0：必须补齐

1. **一份可追问的 PRD**：目标用户、核心场景、问题证据、目标与非目标、流程、规则、异常状态、指标、埋点和验收标准。
2. **真实需求验证**：至少 10–15 名目标用户的访谈/任务测试，不以朋友口头说“不错”作为结论。
3. **可汇总的数据底座**：当前 Umami 能记录事件，但推荐反馈主要保存在用户浏览器 `localStorage`，无法跨用户汇总，也无法直接完成 SQL 分析。
4. **一组真实基线数据**：访问—开始—完成—反馈—分享漏斗，推荐正向率、重选率、拒绝原因分布和接口成功率。

### P1：形成竞争力

5. **推荐质量评估**：30–50 个固定测试场景的离线评估，加上真实用户的“想看/不想看”在线反馈。
6. **一次前后对照实验**：例如比较四问版与三问版、单结果与镜子/窗户双结果，明确假设、观察周期、指标和结论。
7. **一次冷启动复盘**：不同渠道、不同内容钩子的访问、激活、正向反馈和分享数据，而不是只讲曝光量。

### P2：锦上添花

8. 次日/7 日回访、收藏片单、跨设备身份、推荐历史等留存能力。
9. 轻量学习排序；在积累 500–1000 条有效反馈前，不需要训练复杂模型。

## 四、PRD 应该怎么写

建议写一份 6–10 页的 `FilmMirror v1.0 PRD`，结构如下：

1. 背景与问题：用户在“今晚看什么”和“借片单表达自我”中的决策困难。
2. 目标用户：18–28 岁、每月至少观影 2 次、愿意分享片单或经常选择困难的用户。
3. 核心场景：临时选片、片单人格分享；把两条路径分开描述。
4. 目标与非目标：首阶段验证推荐可信度和完成率，不做播放、购票、长影评社区。
5. 用户流程：入口—输入—推荐—解释—反馈—分享/重选。
6. 推荐规则：输入权重、硬筛选、软排序、镜子/窗户差异、降级策略。
7. 异常与边界：接口失败、海报失败、候选不足、重复推荐、用户跳过问题。
8. 指标与埋点：事件名称、触发时机、属性、成功口径和护栏指标。
9. 验收标准：功能、性能、推荐质量、无障碍和上线检查。
10. 版本计划与风险：P0/P1/P2、版权和隐私、第三方 API 稳定性。

## 五、冷启动方案

### 第一层：种子验证，目标 30–50 个有效用户

- 渠道：校内电影社团、同学群、朋友圈一对一邀请。
- 做法：不发泛广告，给出明确任务：“用 3 分钟完成一次推荐，并回答 4 个问题”。
- 目标：15 人完成可用性测试；30–50 人完成至少一条流程；获得 10 条可归类的文字反馈。
- 优点：容易追访，能观察用户为什么退出、为什么不信推荐。

### 第二层：内容验证，目标比较两个内容钩子

- 小红书钩子 A：`我用片单测了一下自己的电影人格，结果像吗？`
- 小红书钩子 B：`选片 30 分钟，看片 10 分钟？我做了个今晚选片器。`
- 每个钩子做 3 个内容版本，统一落到正式站，但使用不同 `utm_content`。
- 观察访问→开始、开始→结果、正向反馈和分享，不以点赞量替代产品转化。

### 第三层：高质量反馈

- 在即刻、产品/独立开发者社区发布完整复盘，目标是获取产品和算法反馈。
- 豆瓣更适合作为用户研究和电影讨论来源，不作为主要导流渠道；发布内容需符合社区规则，避免广告式刷屏和诱导互动。

### UTM 示例

`https://film-mirror.pages.dev/?utm_source=xhs&utm_medium=social&utm_campaign=coldstart_v1&utm_content=persona_a1`

## 六、数据架构

### 保留 Umami

用于页面访问、UTM、基础事件、渠道漏斗和快速看板。项目已经接入 Umami，不需要重复造一套流量统计。

### 增加 Cloudflare D1

用于保存匿名产品事件和反馈明细，并直接用 SQLite 兼容 SQL 分析。D1 与当前 Cloudflare Pages 技术栈一致，改造成本低。

当前缺口：`daily_feedback` 虽会发给 Umami，但明细只存本机；换设备或换用户后无法形成统一数据集。下一版应增加 `/api/events`，只接收白名单事件并写入 D1。

最小字段：

- `event_id`：事件唯一 ID。
- `anonymous_id`：浏览器生成的匿名 ID，不收姓名、手机号和 IP。
- `session_id`：一次访问会话。
- `event_name`：标准事件名。
- `flow`：A 或 B。
- `occurred_at`：事件时间。
- `utm_source / medium / campaign / content`：渠道归因。
- `variant`：实验版本。
- `movie_id / result_mode`：推荐对象与镜子/窗户轨道。
- `properties`：JSON 扩展字段。
- `app_version`：上线版本。

## 七、首轮事件表

| 事件 | 触发时机 | 核心属性 |
|---|---|---|
| `visit` | 首次进入 | UTM、版本、设备类型 |
| `flow_start` | 点击任一路径 | flow |
| `input_complete` | 完成输入 | flow、耗时、选项数量 |
| `result_view` | 推荐稳定展示 | flow、候选池、轨道、电影 ID |
| `recommendation_feedback` | 想看/看过/不想看 | action、reason、轨道、电影 ID |
| `reroll` | 点击两部都换 | 上一轮电影 ID、轮次 |
| `share` | 复制/下载分享内容 | share_type、轨道 |
| `poster_error` | 海报最终失败 | movie_id、来源 |
| `api_error` | API 调用失败 | endpoint、status、fallback |

不要采集每次鼠标点击；只采集能回答产品问题的事件。

## 八、必须回答的 SQL 问题

1. 各渠道的访问、激活、正向反馈和分享转化率分别是多少？
2. Flow A 与 Flow B 哪条路径完成率更高，流失发生在哪一步？
3. 镜子与窗户的“想看率”是否存在显著差异？
4. 哪些拒绝原因最多，是否集中在某类输入或电影类型？
5. 用户重选次数越多，最终正向反馈率是上升还是下降？
6. 海报/API 失败是否显著降低结果页完成率？
7. 不同内容钩子带来的用户质量是否不同？

示例 SQL 见 `docs/analytics_queries.sql`。

## 九、四周时间线

### 第 1 周：PRD 与数据底座

- 写完 PRD、事件字典和口径表。
- 修复 Production Secret；创建 D1、`events` 表和 `/api/events`。
- 校验 Umami UTM；用测试数据跑通 6 条 SQL。
- 验收：事件不重复、关键字段不为空、正式站 API 200。

### 第 2 周：15 人任务测试

- 每人完成两条路径；记录完成时间、卡点、推荐评分和拒绝原因。
- 做访谈问题归类与优先级矩阵。
- 验收：至少 10 份有效记录，形成一条高优先级迭代假设。

### 第 3 周：冷启动实验

- 校内种子用户 + 小红书 2 个钩子 × 3 个素材版本。
- 每个链接使用独立 UTM；每天只做数据检查，不随意改口径。
- 验收：累计 50 个有效激活、20 条推荐反馈、10 条文字反馈；不足时如实记录样本限制。

### 第 4 周：迭代与面试案例

- 针对最大问题上线一个版本，比较前后 7 天或同周期指标。
- 整理 6 页案例：问题、研究、方案、规则、数据、复盘。
- 准备 3 分钟与 8 分钟口述，并保留 SQL 截图、看板和用户原话作为证据。

## 十、面试叙述升级

不要只说“我做了一个电影推荐网站”。建议使用：

> 我从个人选片困难出发做了 FilmMirror MVP，但首轮自测暴露了推荐输入断裂、页面性能和数据不可验证三个问题。我先重构统一推荐规则与镜子/窗户双轨解释，并用 Cloudflare Functions 解决第三方 API 与降级；随后搭建访问—推荐—反馈—分享漏斗，通过种子用户和两组内容钩子验证激活与推荐正向率，再用 SQL 分析渠道质量、拒绝原因和重选行为，驱动下一轮迭代。

在拿到真实数据前，只把数值写成“目标”或“计划”，不要把目标值包装成已完成成果。
